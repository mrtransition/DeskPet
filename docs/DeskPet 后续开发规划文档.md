## 1. 文档目的

本文档基于 DeskPet 当前项目定位、功能矩阵与公开文档梳理，明确后续开发总体策略、阶段路线、工作包优先级、验收标准与治理机制，用于指导后续版本规划与开发执行。

核心判断：DeskPet 的项目目的与现有功能之间存在局部设计张力，但未构成结构性冲突；项目已通过“产品相关性收敛”策略进行主动调和。后续开发应继续坚持“强化核心、收敛边界、深化信任、审慎扩展”的总体方向。

## 2. 项目定位与现状判断

### 2.1 核心定位

DeskPet 的核心目的是成为**轻量、私密、点击即聊的桌面 AI 聊天宠物**。其关键特征包括：

- 形态轻：透明置顶、不入任务栏，主程序保持轻量；
- 交互简：点击弹出对话，右键切换皮肤与人格；
- 能力专：多模型流式聊天，强调密钥零泄露与数据本地化；
- 体验有趣：桌面宠物动画、皮肤包、人格切换。

### 2.2 现状判断

当前功能已覆盖宠物基础体验、AI 对话增强、工具调用、自然语言提醒、语音朗读、健康提醒、安全与隐私等多个维度，功能丰富度较高。

主要张力集中在三处：

1. **工具调用与纯聊天边界模糊**：AI 从“对话者”扩展为“执行者”，扩大攻击面；
2. **附加功能稀释轻量专注体验**：健康提醒、语音朗读等与核心聊天链路关联较弱；
3. **皮肤系统复杂度与轻量宣传存在反差**：换肤引擎能力较深，增加维护成本。

项目 Roadmap 已提出“产品相关性收敛”，说明维护方已意识到功能膨胀风险。后续规划应将该策略制度化、常态化。

## 3. 总体策略与开发原则

### 3.1 三条主线

后续开发围绕以下三条主线展开：

1. **做减法以强化核心**：资源优先投入“点击即聊”核心体验，控制非核心功能默认开启与功能膨胀；
2. **做深安全以建立信任**：将隐私与安全从良好实践升级为可验证、可查阅、可撤销的信任资产；
3. **做活生态以延长生命周期**：以皮肤、人格创作和社区策展为杠杆，审慎推进扩展能力。

### 3.2 开发原则

- **核心优先原则**：任何新功能须说明其与“轻量桌面 AI 聊天宠物”核心目的的直接关系；
- **默认关闭纪律**：偏离核心聊天链路的新增功能默认关闭，归入“实验性增强”，并提供清晰说明与风险提示；
- **安全可验证原则**：安全承诺应文档化、可查阅、可撤销，避免仅停留在口号；
- **最小攻击面原则**：新增系统集成点须经过安全评审，不相关集成即使技术可行也应放弃；
- **Windows 优先原则**：短期巩固 Windows 体验完整性与稳定性，跨平台作为架构预留而非短期目标；
- **轻量约束原则**：技术选型服务于“轻”，审慎引入重型依赖；
- **透明收敛原则**：版本发布不仅说明新增内容，也说明移除内容及原因，形成持续的设计哲学沟通。

## 4. 阶段路线图

### 4.1 短期（0—3 个月）：巩固核心与治理基线

**目标**：建立功能准入与安全治理基线，防止功能膨胀，明确工具调用边界。

重点任务：

1. 将“功能开关默认值纪律”制度化，形成需求准入检查清单；
2. 明确工具调用能力边界，将工具限定在轻量辅助范畴，审慎评估文件系统读写、命令执行等高危能力；
3. 编制《隐私与安全白皮书》初版，系统化说明数据流向、密钥生命周期、工具调用授权与本地日志策略；
4. 建立新增系统集成点的安全评审流程；
5. 版本发布说明纳入“移除或收敛内容及原因”；
6. 评估皮肤与人格创作工具链的易用性改进空间。

### 4.2 中期（3—6 个月）：体验深化与安全治理

**目标**：提升核心陪伴体验的协同性，缓解授权疲劳，补齐本地可观测性。

重点任务：

1. 试点“人格—皮肤—记忆”联动：人格影响回复语气、动画状态与记忆提取偏好；
2. 审慎试点情境感知陪伴：基于已授权轻量信号提供情境相关搭话，坚持默认关闭、点击处理、持续可感知授权；
3. 引入细粒度授权策略与授权撤销面板，缓解“授权疲劳”；
4. 建立纯本地、用户可选的诊断日志与一键诊断包生成能力；
5. 抽象平台相关代码适配层，为未来跨平台预留架构空间；
6. 社区皮肤/人格画廊 MVP，采用官方策展或轻量静态页面形式。

### 4.3 长期（6—12 个月及以上）：生态审慎扩展与信任资产完善

**目标**：在核心体验与安全治理成熟前提下，审慎评估受限扩展能力。

重点任务：

1. 评估受限的、经过审核的“技能”扩展形式，不引入无限制通用插件系统；
2. 审慎评估 macOS/Linux 支持，不以跨平台本身作为短期目标；
3. 完善可验证安全资产，包括隐私白皮书迭代、漏洞披露流程、授权审计本地自查能力；
4. 持续维护轻量约束，监控主程序体积与依赖复杂度；
5. 建立社区贡献指南，吸引认同克制设计理念的贡献者。

## 6. 明确不做与审慎事项

为保持项目定位清晰，后续开发应明确以下边界：

1. **不新增偏离核心且默认开启的功能**；
2. **短期不引入通用插件系统**，避免打开功能膨胀闸门；
3. **不轻易引入文件系统读写、命令执行等高危工具能力**，如确需引入，须建立命令黑名单、沙箱化工作区、人机协同确认等多层防线；
4. **不将跨平台作为短期目标**，避免稀释 Windows 核心体验打磨精力；
5. **不引入与轻量定位冲突的重型依赖**，如复杂物理引擎、3D 渲染库等；
6. **不保留与核心目的关联度低且维护成本高的功能**，按“产品相关性收敛”原则持续修剪。

## 8. 风险与缓解措施

| 风险 | 表现 | 缓解措施 |
|---|---|---|
| 功能膨胀 | 非核心功能累积，稀释点击即聊体验 | 默认关闭纪律、需求准入清单、产品相关性收敛 |

| 社区内容质量 | 皮肤/人格作品质量参差 | 官方策展、格式校验、冲突检测 |
| 维护成本上升 | 换肤引擎与附加功能复杂化 | 持续收敛、轻量约束、移除低相关功能 |

## 9. 治理与执行机制

### 9.1 需求准入检查清单

每个新增需求在进入开发前，应回答以下问题：

1. 是否直接服务于“轻量桌面 AI 聊天宠物”的核心目的？
2. 是否默认关闭或归入实验性增强？
3. 是否扩大攻击面？如扩大，是否经过安全评审？
4. 是否可被用户随时撤销或关闭？
5. 是否显著增加主程序体积、依赖复杂度或维护成本？
6. 是否与现有功能产生协同，而非单纯堆叠？

任一问题回答不明确时，应暂缓进入开发或降级为评估事项。

### 9.2 安全评审机制

新增工具、感知源、系统集成点须经过安全评审，评审内容包括：数据流向、权限范围、授权方式、撤销能力、日志与审计、失败降级策略。高危能力须额外设计多层防线。

### 9.3 版本发布与文档维护

- 版本发布说明应包含：新增功能、收敛或移除内容及原因、安全相关变更；
- 隐私与安全白皮书随安全设计变更同步更新；
- 本文档按季度或重大版本节奏复审，必要时修订版本号；
- 所有重大取舍应形成决策记录，便于后续维护者理解设计哲学。

## 10. 结论

DeskPet 已跨过功能建设阶段，后续核心命题是“从丰富到卓越”。卓越不来自更多功能，而来自核心体验的深度打磨、安全信任的可验证构建以及社区生态的有机生长。后续开发应继续握紧“收敛”这把剪刀，将资源集中在让“点击即聊”的桌面 AI 小猫更聪明、更可信、更有温度上。

本规划文档作为后续开发、评审与版本规划的基线文件，由项目维护者负责解释与更新。
