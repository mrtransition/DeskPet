# 安全评审流程

> 工作包：P-04 新增集成点安全评审流程
> 版本：v1.0（2026-11-13）
> 适用：新增 / 变更工具、感知源、系统集成点、外部输入解析、新出站域名、新系统依赖
> 关联：[工具调用能力边界](工具调用能力边界.md)、[隐私与安全白皮书](隐私与安全白皮书.md)、[评审登记表](安全评审/README.md)

## 1. 目标

确保每一个扩大攻击面的改动，在合并前都有**可查阅的评审记录**，而不是靠 Review 时的口头判断。评审记录同时承担三个作用：

1. 让维护者在下一次修改前知道当初为什么这样设计；
2. 让用户与贡献者可以核对安全承诺；
3. 让“最小攻击面”从原则变成可执行的门禁。

## 2. 触发条件

出现以下任一情况，必须新增 `INT-xxx` 评审记录：

| 类别 | 示例 |
|---|---|
| 新工具 | 模型可调用的新函数、新参数域、新副作用 |
| 新感知源 | 剪贴板、截图、麦克风、摄像头、窗口标题、文件变化、系统事件 |
| 新系统集成点 | 托盘、全局快捷键、开机自启、单实例、协议处理器、文件关联、通知 |
| 新外部输入 | 皮肤包、人格包、配置文件、更新清单、日志导入等解析入口 |
| 新出站域名 | 任何不在现有白名单中的网络目的地 |
| 新系统依赖 | 需要额外权限、驱动、服务、运行时或原生库的依赖 |
| 权限扩大 | 已有能力增加参数、放宽白名单、延长授权、增加默认允许 |

仅仅修改文案、样式、性能或内部重构，不触发评审；但如果重构改变了信任边界，按“权限扩大”处理。

## 3. 角色与职责

| 角色 | 职责 |
|---|---|
| 需求提出者 | 填写评审记录初稿，说明数据流与最小权限方案 |
| 实现者 | 提供代码位置、测试与失败降级；确保实现与记录一致 |
| 评审人 | 核对六个评审维度，给出通过 / 条件通过 / 拒绝结论 |
| 维护者 | 登记评审编号、合并 PR、在发布说明中披露安全相关变更 |

单人维护阶段，评审人由维护者担任；涉及高危能力时，应在 PR 中公开征求社区意见，并至少保留 7 天评审窗口。**回溯评审记录不得伪装成独立第三方审计**，需在记录中注明评审方式。

## 4. 评审流程

```text
1. 触发识别
   └─ 需求 / PR 是否命中第 2 节任一条？
2. 起草记录
   └─ 复制 _模板.md → INT-xxx-<slug>.md，填写数据流、权限、授权、撤销、日志、降级
3. 风险评级
   └─ 低 / 中 / 高，高风险必须列出多层防线
4. 评审结论
   └─ 通过 / 条件通过（列前置条件）/ 拒绝
5. 登记
   └─ 更新 安全评审/README.md 登记表，PR 引用编号
6. 实现与验证
   └─ 参数白名单、失败关闭、回归测试、文档同步
7. 发布披露
   └─ 发布说明“安全与隐私变更”写明新增 / 变更 / 移除
```

**门禁：** 没有评审记录的新工具 / 感知源 / 系统集成点，不得合并；条件通过的前置条件未完成，不得合并。

## 5. 六个评审维度

| 维度 | 必须回答的问题 | 不合格表现 |
|---|---|---|
| 数据流向 | 读取什么？发送到哪里？是否落盘？是否进入模型上下文？ | “可能会用一下”但说不清去向 |
| 权限范围 | 需要哪些系统权限？是否可用更小权限完成？ | 为方便申请超出需要的权限 |
| 授权方式 | 何时询问？是否可记忆？默认允许还是拒绝？ | 默认允许敏感能力；无法逐次授权 |
| 撤销能力 | 用户在哪里关闭？是否立即生效？关闭后是否仍有后台行为？ | 只能改配置文件；关闭后仍运行 |
| 日志与审计 | 记录什么？是否含敏感内容？用户能否查看与清除？ | 把对话正文、剪贴板、Key 写进日志 |
| 失败降级 | 超时、拒绝、解析失败、网络失败时怎么办？ | 失败后“尽力执行”或静默重试高危动作 |

## 6. 风险评级

| 等级 | 判定标准 | 最低要求 |
|---|---|---|
| 低 | 仅本地、无敏感数据、无持久副作用，或只影响应用自身状态 | 默认询问 + 可撤销 + 基本测试 |
| 中 | 读取敏感本地数据、启动本地程序、访问固定外部服务、解析外部文件 | 默认询问或拒绝 + 白名单 + 超时 + 失败关闭 + 回归测试 |
| 高 | 任意文件读写、命令执行、凭据访问、持续采集、任意出站、提权 | 默认不存在；如引入须满足《工具调用能力边界》第 4 节八层防线，且不得提供“始终允许” |

当前 DeskPet 不含高风险工具。

## 7. 记录规范

- 文件命名：`docs/治理/安全评审/INT-<三位序号>-<kebab-slug>.md`；
- 编号只增不减，不复用；移除能力时保留记录并标注“已移除”；
- 每份记录必须包含：能力概述、数据流向、权限范围、授权与撤销、日志与审计、失败降级、风险评级、防线、结论、验证与复审；
- 记录中的代码位置使用相对路径或函数名，便于后续核对；
- 结论变更时新增“复审”小节，不覆盖原结论。

## 8. 复审触发

- 能力参数、白名单、默认授权发生变化；
- 出现安全事件、绕过路径或用户投诉；
- 依赖升级改变了底层行为；
- 发布说明中的安全承诺发生变化；
- 至少每年对高风险 / 中风险记录做一次集中复审。

## 9. 与发布流程的衔接

发布说明必须包含“安全与隐私变更”章节，列出：

- 新增 / 变更 / 移除的 `INT-xxx` 记录；
- 默认授权、白名单、出站域名的变化；
- 未完成的安全事项（不得隐藏）。

没有安全相关变更时写“本版本无”，不得省略章节。
