# 发布说明规范

> 工作包：P-05 发布说明透明收敛机制
> 版本：v1.0（2026-11-13）
> 适用：所有对外版本（含补丁版）
> 关联：[发布说明模板](发布说明模板.md)、[需求准入检查清单](需求准入检查清单.md)、[发布说明归档](../releases/README.md)

## 1. 原则

版本发布不仅说明“新增了什么”，也必须说明“移除了什么、为什么”。这是“透明收敛”的核心：让用户与贡献者理解 DeskPet 的设计哲学不是“功能越多越好”。

四条硬性要求：

1. **每次发布都有“收敛与移除”章节**；没有内容时写“本版本无”，不得省略；
2. **移除必须写原因**，不能只写“已移除”；
3. **安全相关变更必须单列**，包括默认值、授权、白名单、出站域名与未完成事项；
4. **发布说明与代码、README、ROADMAP、版本号一致**，不夸大、不隐藏。

## 2. 发布说明结构

按以下顺序输出，缺一不可：

| 章节 | 内容 | 示例 |
|---|---|---|
| 标题 | `vX.Y.Z — 一句话主题` | `v2.3.0 — 智能去除背景与皮肤导入收敛` |
| 摘要 | 2–4 句：本版本最重要的一件事与取舍 | 说明“新增什么、收敛什么” |
| 新增 | 新能力、增强、需求编号 | 每条写清用户价值与入口 |
| 修复 | Bug 修复与回归测试 | 写触发条件与结果 |
| 收敛与移除 | 移除 / 合并 / 降级 / 默认值变化 + 原因 | **必填**，无则写“本版本无” |
| 安全与隐私变更 | 授权、白名单、出站、密钥、日志、未完成事项 | 引用 `INT-xxx` |
| 验证 | 自动化测试、手工验收、已知限制 | 不写“应该没问题” |
| 升级说明 | 数据迁移、兼容性、需要用户手动做的事 | 无则写“无需手动操作” |

## 3. 写作规则

### 3.1 新增

- 每条以“用户能感知的行为”开头，不先讲实现；
- 标注需求编号（如 `FR-SKN-002`）与默认状态；
- 默认开启的新能力必须写明关闭路径，并链接《默认开启能力清单》。

### 3.2 收敛与移除

必须回答三个问题：

1. **移除了什么**：入口、功能、默认值、依赖或文档；
2. **为什么移除**：与核心目的关联弱、维护成本高、安全风险、重复入口；
3. **用户如何迁移**：替代入口、历史数据是否保留、是否需要手动操作。

示例：

> 移除「导入单张图片」与「导入 Codex 宠物」入口。原因：图片类导入入口重复，增加维护与误用成本；历史皮肤仍可切换与删除。替代方式：使用「导入八态单图（4×2）」或「导入皮肤包」。

### 3.3 安全与隐私变更

- 引用安全评审编号（`INT-xxx`）；
- 写明默认授权与白名单变化；
- 未完成的安全事项必须显式列出（如“更新签名仍未实现”）；
- 不得用“持续加强安全”这类无法验证的表述替代具体变更。

### 3.4 验证

- 写清执行了什么：`cargo test` 数量、前端语法检查、CDP E2E、手工路径；
- 写清已知失败或未覆盖项；
- 性能相关变更给出测试机与数据规模。

## 4. 发布流程

```text
1. 冻结范围
   └─ 对照 ROADMAP / PR 清单确认本版本包含项
2. 汇总准入与评审
   └─ 每个新增项有准入结论；每个集成点有 INT-xxx
3. 对比默认值
   └─ 对照《默认开启能力清单》，记录新增 / 移除 / 变化
4. 起草说明
   └─ 复制 发布说明模板.md → docs/releases/vX.Y.Z.md
5. 自查
   └─ 八个章节齐全；“收敛与移除”非空；安全事项无隐藏
6. 评审
   └─ 至少一名维护者复核；涉及安全变更时对照评审记录
7. 发布
   └─ GitHub Release 正文与 docs/releases/vX.Y.Z.md 保持一致
8. 归档
   └─ 更新 README 版本历史、ROADMAP 基线、版本号
```

## 5. 存放位置

- **归档文件**：`docs/releases/vX.Y.Z.md`，随仓库版本管理；
- **GitHub Release**：正文与归档文件一致；可在归档文件基础上补充下载链接；
- **README 版本历史**：保留摘要与归档链接，不复制全文。

## 6. 自动校验

`scripts/check-governance.mjs` 会检查：

- `docs/releases/*.md` 是否包含八个必需章节；
- “收敛与移除”章节是否为空；
- 治理基线文档是否存在；
- 治理文档中的相对链接是否可解析。

CI 在 `push` / `pull_request` 时运行；本地可用 `node scripts/check-governance.mjs` 自检。

## 7. 反例

| 反例 | 问题 |
|---|---|
| 只写“新增若干优化与修复” | 无法验证，用户不知道改了什么 |
| 移除功能只写“已下线” | 没解释原因，设计哲学断裂 |
| 默认值变化藏在“其他”里 | 用户升级后行为突变且不知情 |
| 安全事项只写“已加强” | 不可验证，违背白皮书承诺 |
| GitHub Release 与仓库文档不一致 | 两个事实来源，后续维护者无法判断 |

## 8. 维护

- 本规范随发布流程变化同步更新；
- 每次发布后复盘：是否有章节缺失、是否有用户误解；
- 归档文件不修改历史内容，勘误以“附注”追加。
